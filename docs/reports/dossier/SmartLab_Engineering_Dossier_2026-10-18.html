Executive summary

The Smart Lab is a FastAPI + PostgreSQL + React portal running in Docker on the lab laptop, with native Windows services for two security cameras (YOLO26s on the GTX 1650 via DirectML), a face server, a local LLM (Ollama, CPU), a project-knowledge service, read-only robot collectors (UR5e RTDE, FANUC web pages), a PC agent, n8n automations (26 workflows) and ESP32 nodes (door master, ESP32-CAM, consumables bin, reusable bin, environment node).

Software state: VERIFIED. The full automated backend suite, the camera/vision suite, the knowledge, PC-agent and robot-monitor suites, TypeScript checks, production builds and browser end-to-end checks pass (section 7). The final evidence run: 41 PASS, 13 FAIL, 7 NOT AVAILABLE, 3 SIMULATION, 4 PHYSICAL VALIDATION REQUIRED, 1 BLOCKED - every FAIL is a physical device that is not connected here.

Most important changes in this round (all deployed, tested; section 3):

  • Data-integrity defect fixed: a resolved camera alert made the next camera event fail (HTTP 500, event and snapshot lost).
  • Safety: a latched robot STOP was silently cleared by a backend restart - now rebuilt from the audit log.
  • Identity: four defects found with a new simulated scenario bench (stale track stealing a runner's name, velocity overshoot swapping neighbours, door naming by timing alone, cross-camera names never shared). 180 simulated runs now show 0 wrong-name frames.
  • Camera protection: one AI answer used every CPU core at above-normal priority and took camera analysis from 7 to 1.7 frames/s; now bounded (4 threads, one answer at a time, cameras above normal priority, instant answers for status questions: ~50 s -> < 0.2 s).
  • Reliability centre: alert grouping and quality, dependency model with what-if simulation, investigation, configuration drift, performance objectives, restore drills, action policy, global search, regrouped navigation, safe deploy script with rollback.

Most important risks: (1) the administrator still uses the published seed password (owner action); (2) the laptop is at its memory limit with everything open (commit 95 %) and its clock drifts ~55 ms/h; (3) no physical camera-identity, robot or ESP32 test has been repeated since 14 Oct - the day plan is in docs/LAB_GO_NOGO_2026-10-18.md.

1. Scope and architecture

Data flows: ESP32 nodes POST heartbeats / telemetry / access events to the backend; camera services post state and events and serve frames that the backend proxies; robot collectors post telemetry (read-only towards the robots); the PC agent posts state and frames and long-polls for viewer / action changes; n8n calls backend endpoints on schedules; the backend serves the portal and the live WebSocket stream.

8. Reliability, security and recovery

  • Alert grouping: fingerprint per condition; repeats counted; reopen within 30 min; MITIGATED; escalation (unacknowledged CRITICAL 15 min / WARNING 4 h, 20 repeats, 3 reopenings). Historical analysis: 376 incidents were only 75 distinct conditions (80 % repeats) - the noise grouping now removes. Safety alarms still notify on every occurrence.
  • Dependency model / what-if: live states per part with evidence class (live / inferred / simulated); likely roots; simulated failure impact and recovery order.
  • Configuration drift: baseline backend/app/config_baseline.json; compliant at the snapshot; secrets checked only for presence / non-default.
  • Performance: per-route p50/p95/p99, regression detection (minimum samples, cooldown), objectives with error budget.
  • Backups: 6-hourly, integrity-checked; restore drill into isolated databases with table comparison; deploy tool with rollback.
  • Security: strong headers, sign-in lockout, authorisation on every route, audit trail. Open: admin on the published seed password (High); HTTP on the LAN (Medium). Details: docs/SECURITY_FINDINGS_2026-10-18.md.
  • Action policy: robot motion, door logic, firmware, safety settings, production data: never automatic. The portal STOP is not a safety-rated emergency stop.

11. Roadmap and hardware recommendations

Immediate (days)

  • Admin password; camera-service restart; clock sync; lab day tests (identity scenarios with the scoring metrics of the bench).
  • Calibrate both floor maps so names can cross cameras; record real ID-switch counts.

Medium term (weeks)

  • ESP32 firmware: bounded offline queue with event ids and capture time, idempotent batch ingestion (backend), RTC.
  • Serve camera frames directly from nginx (or MJPEG) so live viewers do not load the API process.
  • Move Docker services to a small dedicated mini PC: the laptop is at its memory limit with cameras + AI + dev tools.
  • Per-branch power monitoring (INA219) feeding the portal: detect a failing supply before nodes go silent together.

Research ideas (thesis follow-up)

  • Learned re-ID fine-tuned on consented lab data (needs privacy approval); evaluation corpus with ground truth for IDF1 / HOTA.
  • Predictive maintenance only after enough labelled outcomes exist (today: rules + robust baselines).
