## 2. Classification

- **A. Complete:** backups + restore, exact assistant answers and charts, camera software, portal pages, data restore.
- **B. Software complete, hardware unverified:** camera in a real lab, PC auto-detection, PC agent, UR5e collector, smart bins.
- **C. Physically working, needs hardening:** door (power events, 12 V split), environment node (PIR, MQ-2, enclosure).
- **D. Missing:** data provenance, experiment records, alarm escalation, emergency audio extras, PC usage analytics, time-sync audit, FANUC, scheduled email.
- **E. Incorrect or risky:** default secrets (JWT secret, shared device key, DB password); backend port 8000 on all interfaces; 2 maintenance tickets that are software tests in the live data; sessions never record exits.
- **F. Worth improving:** timing-sensitive analytics test; device health fields (uptime, Wi-Fi) for every node.

## 5. Proposed minimum implementation for defensible data

1. `provenance` column on access_events, sensor_readings, alerts, bookings, access_sessions, issues, security_events (REAL_OPERATION, PHYSICAL_TEST, BENCH_TEST, SOFTWARE_TEST, RECOVERED_HISTORY, DEMO_DATA, UNKNOWN_PROVENANCE).
2. A system-wide **data mode** (Settings, admin only) that stamps new rows: BENCH_TEST now, REAL_OPERATION after installation.
3. Backfill only what is provable (recovered rows, the two n8n test tickets); everything else UNKNOWN_PROVENANCE until the owner confirms it was bench testing. Nothing deleted.
4. An `experiments` table (fields from the defensibility prompt) and an experiment run mode that tags rows PHYSICAL_TEST with the experiment ID.
5. Reports and the assistant filter by provenance; thesis analytics use PHYSICAL_TEST with an experiment ID only.
6. Occupancy wording: SESSION_STARTED / EXIT_CONFIRMED / SESSION_ENDED / EXIT_UNKNOWN; reports state that exits are not confirmed.
